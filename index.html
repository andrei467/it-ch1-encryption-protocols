ENCRYPTION · SYMMETRIC

Symmetric encryption: one key, two jobs

The sender encrypts with a key, and the receiver decrypts with the same key. It's fast — which is why it's the default choice for large amounts of data — but that single shared key is also its weak point: however it gets from sender to receiver, that journey has to be secure, and if a bad actor ever captures it, every message encrypted with it is exposed.

TASK 1 · SCENARIO 1 point

A hospital backs up several terabytes of patient scan files to its own internal server overnight. One technician suggests asymmetric encryption; another suggests symmetric. Which would you recommend, and what's the one serious risk that comes with your choice?


MODEL ANSWER

Symmetric is the better fit — it's much faster, which matters when you're encrypting huge volumes of data like scan files. The risk to manage is key distribution: because the same key both encrypts and decrypts, if that key is ever intercepted or leaked, an attacker could decrypt every backup made with it.

ENCRYPTION · ASYMMETRIC

Asymmetric encryption: two keys, split jobs

Asymmetric encryption uses a public key and a private key, created together as a pair that only work with each other. The public key is shared openly and used to encrypt; the matching private key is kept secret by its owner and used to decrypt. It's slower than symmetric encryption, so it's typically reserved for smaller, high-value data like passwords or bank details.

TASK 2 · SCENARIO 1 point

Alice wants to send Bob a confidential message over an insecure email server, and the two of them have never met to exchange a secret key. Walk through what happens to the message, naming which key does which job.


MODEL ANSWER

Bob generates a key pair and shares his public key openly. Alice uses Bob's public key to encrypt her message into cipher text and sends it across the insecure server. Bob then uses his own private key — which he has never shared with anyone — to decrypt it back into plain text. Because only Bob's private key can reverse the encryption, the message stays confidential even though it crossed an insecure channel.

PROTOCOLS

SSL/TLS: encryption in your browser bar

SSL (Secure Sockets Layer) is a protocol that encrypts data sent over the internet, guarding against eavesdropping, tampering, and man-in-the-middle attacks — the sort of protection online payments and login pages depend on. TLS (Transport Layer Security) is its successor: same job, more secure and more efficient. When you see HTTPS in the address bar, TLS (still often called "SSL" out of habit) is doing that work.

In short: your browser and the server agree on how to trust each other, then switch to a fast, shared encryption key for the rest of the session — a symmetric key, set up using asymmetric encryption first, which is why both types matter here.

TASK 3 1 point

A friend says: "The padlock and https:// in my browser mean the website itself is trustworthy and safe to buy from." What does that padlock actually confirm — and what does it not guarantee?


MODEL ANSWER

The padlock/HTTPS confirms that TLS (or SSL) has encrypted the connection between the browser and that server, so data passing between them is protected from eavesdropping and tampering in transit. It does not guarantee the site's owner is honest or that the business is legitimate — a scam site can use HTTPS too. It proves the connection is private, not that the destination deserves your trust.
